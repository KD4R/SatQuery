# ADR-0003: Role-Based Access Control (RBAC) Design

**Status:** Accepted  
**Date:** 2026-09-11  
**Deciders:** Platform Engineering Team, Security Lead  

---

## Context

SatQuery AI is a multi-tenant SaaS platform. Every API operation must be authorised against:
1. **Who is the caller?** (authentication)
2. **What are they allowed to do?** (authorisation / RBAC)
3. **Which tenant's data can they touch?** (tenant isolation)

We needed a model that is simple to enforce, hard to bypass, and maps naturally to real-world satellite operations workflows.

## Decision

We implement a **hierarchical role model** with **tenant-scoped identities**:

```
Role hierarchy (ascending privilege):
  VIEWER < ANALYST < OPERATOR < ADMIN < SYSTEM
```

Each JWT carries an `org_id` claim that is the authoritative tenant scope. Every DB query is mandatory-filtered by `org_id` extracted from the verified token — never from the request body.

## Role Definitions

| Role | Capabilities |
|---|---|
| `VIEWER` | Read missions, AOIs, job status |
| `ANALYST` | VIEWER + create missions, submit analysis jobs |
| `OPERATOR` | ANALYST + manage AOIs, approve/cancel jobs |
| `ADMIN` | OPERATOR + manage users and tenant configuration |
| `SYSTEM` | Machine-to-machine service accounts (AI agents, internal services) |

## OWASP Alignment

- **A01 Broken Access Control**: Every protected route uses `Depends(require_role(Role.X))`. The dependency chain is enforced by FastAPI at request time — handlers cannot be reached without passing the auth gate.
- **A07 Identification and Authentication Failures**: Tokens are cryptographically verified (HS256 in dev, RS256 in prod). `exp`, `iss`, `aud` are all validated. Algorithm is pinned server-side — the `alg` header from an incoming token is **never trusted**.
- **Multi-tenancy (A01 extension)**: `org_id` is extracted only from the verified JWT payload. Any attempt to access another tenant's data returns `404` (resource not found, not `403`) to prevent information leakage about other tenants' existence.

## Service-to-Service (S2S) Identity

Internal services (e.g., AI Agent calling Mission Service) use short-lived `SYSTEM`-role HS256 tokens generated by `packages/auth/jwt.py::generate_s2s_token()`. These tokens expire in 5 minutes and carry an `agent:write` scope that gates the `PATCH /api/v1/jobs/{id}/agent-status` endpoint.

## Consequences

### Positive
- Role hierarchy means a simple `has_role(minimum_role)` check covers all promotion cases — no complex ACL tables.
- `require_role()` is a reusable FastAPI dependency factory — adding a new protected route takes one line.
- Tenant isolation is enforced at the data layer via `org_id` in every repository query — impossible to bypass through the API.

### Negative / Mitigations
- Coarse-grained roles may require fine-grained permissions for future audit requirements. Mitigated by the `Permission` enum already defined in `packages/auth/models.py` for future ACL extension.
- No runtime role changes without token re-issuance. Accepted: short-lived tokens (15 min default) make this acceptable.

## Alternatives Considered

| Option | Reason Rejected |
|---|---|
| Flat permission list (no roles) | Unmanageable as team and endpoints grow |
| Attribute-based access control (ABAC) | Overkill for P1; can evolve from RBAC |
| Database-stored roles per request | Adds DB round-trip per request; stateless JWT is sufficient for P1 |
